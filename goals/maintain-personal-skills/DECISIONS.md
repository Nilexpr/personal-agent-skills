## 统一维护

- **revise 以 writing 的文本评审和 Matt 同类 skill 的主体结构为共同规范，项目 AGENTS.md 提供调用入口和关联维护要求。**
  - Basis: 用户于 2026-10-12 明确需要用 writing 重新审视文本，并以[指定会话](codex://threads/01a123c3-8060-7801-a8c8-89ebbf8b9021)中对 Matt 实际 skills 的组织分析为参考，使本项目 skills 的行文方式相对统一；随后澄清结构参考只覆盖 writing 之外的部分，并授权按 writing-for-agents 与 writing 全量优化 revise、全局安装。
  - Scope: writing 负责完整修订文本及必要附属说明的评审，revise 不重复其原则；主体结构依据任务性质选择并读取 Matt 同类实例，参考入口为项目 references/matt-skills/README.md，不固定所有 skill 的章节模板。structure 与依赖 CLI 继续承担记录和工具职责；命名、体量等项目约束保留在维护 Goal，由 AGENTS.md 引用，无需整体迁移。

## structure

- **structure 的记录根默认使用当前会话工作区；用户或调用流程明确指定其他记录根时，使用指定路径。**
  - Basis: 用户于 2026-10-12 确认跨项目调用 revise 时应能维护 skills 源码及记录，并明确“默认是在当前工作区，如果有特殊指定就按特殊指定的路径”。
  - Scope: 相对的记录根路径以当前会话工作目录解析，记录文件路径以选定记录根解析；未指定时沿用既有行为。revise 将确定的维护工作区传给 structure，记录不因会话起点不同而落到无关项目。

- **structure 根据预期结果、范围、约束和满足条件选择目标，并随工作展开重新判断归属。**
  - Basis: 用户于 2026-10-09 指出依赖管理工具已适合独立建目标，随后批准拆分及目标选择规则修订；原先“只为不相关工作提出新目标”的限制会排除相关但已有独立结果的工作。
  - Scope: 同一结果的工作复用目标；已有可独立判断的结果并需要持续跟踪时，提出独立目标，即使它服务于已有目标或属于同一项目。

## revise

- **revise 用于本项目 skills 的全部改动，范围由源码项目确定，设计预期先从已有目标与 Decisions 中读取。**
  - Basis: 2026-10-09 的初版以实际反馈为入口；用户于 2026-10-12 明确扩展到全部改动，限定为本项目中的 skills，并要求先读取已存档的设计决定，有冲突再提出。用户随后确认跨项目会话支持，工作区默认取当前目录，特殊指定时采用指定路径。
  - Scope: 覆盖新增、修改、重构、改名与移除，包括必要的附属文件；安装副本用于核对，实际修改源码。定位到默认或指定的维护工作区后，读取其 AGENTS.md 和引用规范，并将该工作区明确传给 structure 作为记录根。沿用已确认设计，明确处理新的定位变化；是否另建 skill 根据独立职责或调用需要判断。

- **revise 在改动时完整检查受影响的 skill；写入前展示具体修改，已有明确实施授权时在该范围内保存，否则确认修改稿后写入。**
  - Basis: 用户于 2026-10-09 要求完整检查并展示修改稿；2026-10-12 将 revise 扩展为全部改动的入口，沿用既有评审与展示约定。确认设计预期与授权实施仍需区分。
  - Scope: 完整检查不要求改写无关部分；新增时先检查已有相邻能力。修改用“原文”“修改后”两列展示完整相关段落，保留其他会话的无关改动，范围或前提变化时重新判断授权。

- **每次 skill 修订应用到源码前，先用不继承编写讨论的独立会话评估完整候选稿能否被理解。**
  - Basis: 用户于 2026-10-12 要求修改尚未正式应用时，先交给新 session，检查它能否在没有本次讨论上下文的情况下理解 skill 要做什么，通过后再继续。
  - Scope: 评审输入仅含候选稿及正常使用时可获得的必要引用，不附作者预期答案；比较评审者的理解与已确认设计预期，存在实质理解缺口时修订后重新独立评审。影响含义或必需上下文的后续改动需重评，缺少独立会话或必要材料时保留未应用稿。理解评审不等于原场景重放或实际行为验证，既有改动展示与授权要求继续适用。

- **revise 第一版在确认稿保存、静态检查和结果记录完成后结束，不将重组 prompt 的子会话回复作为历史场景重放验证。**
  - Basis: 用户于 2026-10-09 要求排除维护讨论影响、保持出错前上下文一致且可检查；本次子 agent 演示只重建了部分历史材料，无法保证这些条件，用户接受无法满足时改完即停。
  - Scope: 格式、引用、文本一致性检查不证明行为改善；行为效果明确保留为未验证。

## learn

- **learn 围绕学习者希望能够解释、完成或判断的结果，安排有依据、可调整并能跨会话继续的学习。检查形式与强度由目标和参与方式决定，教学结束与目标达成分别判断。**
  - Basis: 用户于 2026-10-12 基于该设计初衷要求完整评审，并授权按发现的问题优化；评审发现连续阅读、自主学习与统一互动及迁移检查之间的适用条件不清。
  - Scope: 保留来源核查、提问依据及学习证据要求；允许延后或拒绝检查并保留未验证状态。单元仍具有独立可检查的结果，章节仍组织相关单元，但章节结束不再一律要求陌生综合任务，仅在目标需要整合或迁移时使用；讲解顺序按当前问题与前置条件调整。

- **learn 的长期记录只保留影响后续教学、目标判断或恢复的信息，关键证据关联目标、成立条件和帮助情况；材料实质更正后复核受影响的教材及学习结论。**
  - Basis: 同次评审指出全量过程记录的维护负担，以及来源、更正和已记录学习结果之间的缺口；用户授权据此优化。
  - Scope: learn 维护学习计划、教材和学习证据，已有共享目标、决定、偏好和术语沿用 structure 的权威记录。视觉建模沿用下方 visualize 的既定分工，learn 负责教学与评估；浏览器产物按当前问题或课程规模组织。

## writing

- **agent 产出的文档应遵循 writing 的适用规范，包括发送给其他 session 的提示词。**
  - Basis: 用户于 2026-10-10 提出，这些文本用于沟通或反复读写，希望保持共同的基础写作约定。
  - Scope: 按文本的用途判断适用要求，覆盖保存成文件的文档和跨 session 传递的提示词。

- **writing 的评审覆盖请求范围内的适用原则，结论以文本或观察结果为依据，并指出未决的行为问题；评审 agent 指令时，在该范围内逐句寻找 no-op 候选。**
  - Basis: 用户于 2026-10-09 确认采用两份独立评审的修改建议，并要求实施和全局安装。
  - Scope: 评审范围与完成条件；行为实验按实际疑点开展。

- **writing 的正文应使未参与设计讨论的会话能够独立理解并使用其中的指导。**
  - Basis: 用户于 2026-10-09 指出当前版本依赖对话前提，要求补足成本、指针、分支等概念及规则依据。
  - Scope: 文档采用的特定概念在首次需要时定义，相关理由和适用条件就近说明；通用知识按预期读者判断是否需要解释。

- **writing 以准确支持内容用途、降低获取、理解和使用信息的成本为目标，按用途与成本、表达与组织、检查与修正组织统一指导。**
  - Basis: 用户于 2026-10-09 确认按这三部分重新组织已选原则，并要求产出初版。
  - Scope: 人的可读性与 agent 的准确使用共同作为质量要求；专项修正根据适用条件和实际效果采用。

- **writing 默认 agent 具备通用知识，保留理解用途、概念、设计理由和取舍所需的解释，在含义清楚、准确、完整的前提下精简文字。**
  - Basis: 用户于 2026-10-09 要求减少无效解释，并在审阅初版后明确需要说明设计初衷，确认字数要求的优先级低于清楚表达含义。
  - Scope: writing 的统一指导与自身正文；必要解释按实际读者和用途判断。

- **writing 先采用统一指导，覆盖日常聊天与文档写作，不按读者或用途预先拆分。人的可读性与 agent 对含义和要求的准确理解共同作为核心要求，精简以保留必要含义为前提。**
  - Basis: 用户于 2026-10-09 选择先统一使用，重视人的可读性，暂不拆成多个用例。
  - Scope: 当前 writing 的设计与试用；后续依据实际问题决定是否需要区分。

- **writing 提取 Matt 的指针约束、信息层级与集中组织、完成条件、引导词、正向表达和精简规则。**
  - Basis: 用户于 2026-10-09 重读 writing-for-agents 后明确选择这六部分，指出自身概念命名与 Decisions 表达中需要改进的问题。
  - Scope: 用于统一写作指导的设计；执行序列隔离作为有条件试用的方法，适用条件与效果验证要求一并保留。

- **组织内容时权衡常驻上下文与人的记忆、查找和选择成本；每个含义集中维护一个权威来源；指令的行为效果通过具体任务中的实际使用判断。**
  - Basis: 用户于 2026-10-09 确认在六项提取内容中补充两种成本、唯一可信来源和行为效果验证。
  - Scope: 用于 writing 的组织、精简与修订；文本审查判断表达与结构，实际使用验证行为效果。

- **保留完整信息，共同条件和定义只解释一次，其他位置明确引用；按内容关系灵活使用 Markdown 组织表达。**
  - Basis: 用户选择共同条件集中说明，并接受有序列表、无序列表及其他 Markdown 语法，希望降低理解时需要同时处理的上下文。

- **围绕当前任务推进，自行处理可解决的问题，集中提出仍需确认的事项，并清楚说明完成状态和错误。**
  - Basis: 用户认可 i-have-adhd 的抑制旁支、自行解决途中问题、展示完成结果和客观说明错误等实践，以及直接进入内容、避免重复收尾的表达方式。

- **参考 wait-what、i-have-adhd、writing-for-agents 和 [OpenAI 的 skill 设计指导](../../references/rethinking-skills-and-prompts-for-gpt-6-astra.md)；ASD-STE100 只借鉴表达原则，不参考 Waza write。**
  - Basis: 用户明确选择上述参考范围，并因场景不适用和阅读负担排除 Waza write。
  - Scope: 仅适用于 writing 的设计和维护。

## visualize

- **visualize 以通用方法从材料中提取主体、层次、关系及变化，形成可探索、可追溯依据的视觉模型。**
  - Basis: 用户明确希望能力本身通用，所举例子用于说明预期效果，不应逐项追加为领域规则或收窄适用范围。
  - Scope: visualize 的整体定位、设计流程与验证；表达方式和证据要求由具体材料决定。

- **由 agent 根据用户的理解目标和材料，自主判断是否需要交互、选择交互形式与必要操作。**
  - Basis: 用户明确说明，重点是在没有指定具体交互形式时，让 agent 自行判断哪些交互有帮助、采用什么方式更合适。
  - Scope: 用于 visualize 的设计和参考比较。

- **本仓库的 skill 命名为 visualize，面向独立交付，不以聊天内呈现为目标。**
  - Basis: 用户于 2026-10-08 明确要求将 visual-explaining 改名为 visualize，并说明无需遵循官方同名 skill 的聊天内呈现约束。
  - Scope: 本仓库 visualize 的命名、设计和实现。

- **visualize 保持独立，当前主要供 learn 调用，也支持其他 skill 复用其产物。**
  - Basis: 用户于 2026-10-08 重新明确，希望在 learn 中使用，同时将实现保持为独立 skill。
  - Scope: visualize 的职责与调用关系。

- **visualize 依赖 structure 的 GLOSSARY.md 确定相关概念，结合上下文判断概念关系，自主选择视觉与交互方式，交付可独立使用或集成的页面、组件。**
  - Basis: 用户于 2026-10-08 明确输入、处理过程及产物要求，希望先形成简单且能自行完成的闭环。
  - Scope: visualize 的输入、工作流程及交付要求。

- **visualize 单独维护最简设计规范，明确整体排版和交互方式，不规定字号等细节。**
  - Basis: 用户于 2026-10-08 明确要求将这些要求单独成文。
  - Scope: visualize 的浏览器页面与组件设计。

- **visualize 随 skill 提供官方默认 CSS，供独立浏览器页面使用。**
  - Basis: 用户于 2026-10-08 同意加入已核查的官方默认样式资源。
  - Scope: 默认样式资源；嵌入已有项目的组件优先沿用项目样式。

## Skill 编写参考

以下参考由用户于 2026-10-09 分两轮确认保留，合并重复内容后共八项，供后续设计和评审时参考；是否采用及采用方式由具体工作流决定，不作为所有 skill 的统一强制步骤。后续评审可优先检查是否能发现实际矛盾、行动条件是否明确、产物职责是否清楚。

- **说明可以先写实际能力，再写适用场景，保持简短且触发准确。**
  - Basis: [Astra 文章的 Better skills](../../references/rethinking-skills-and-prompts-for-gpt-6-astra.md#better-skills)明确要求说明尽量简短、明确何时使用，其正面示例采用这一顺序；反面示例也采用相同顺序，问题在于触发范围过宽。因此，这一顺序是可借鉴的写法，并非文章规定的必需格式。
  - Scope: skill 的 description 编写与评审；优先表达实际能力和适用条件，避免泛化触发范围。

- **需要用户参与判断的内容，可以由 agent 主动提出问题或具体方案，并提供明确的确认入口。**
  - Basis: 用户欣赏 Matt 主动指出歧义、质疑冲突并提出建议的方式，希望许多 skill 保留用户参与。Matt 的 [domain-modeling](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md)要求主动澄清，但术语明确后直接更新文件，并未统一要求所有写入先确认；[Astra 文章](../../references/rethinking-skills-and-prompts-for-gpt-6-astra.md#decision-boundaries)提醒过强的询问要求可能造成不必要的停止。
  - Scope: 在需要用户判断的位置安排确认，区分主动告知、澄清内容和请求写入批准；在已有确认范围内继续完成工作，只将仍需用户判断的事项提交确认。

- **关键动作前可以设置一个会影响后续行为的判断问题，明确继续、跳过或补充澄清的条件。**
  - Basis: Matt 的 [术语表规则](../../references/matt-skills/upstream/skills/engineering/domain-modeling/GLOSSARY-FORMAT.md#rules)要求添加术语前判断它是否属于当前上下文特有的概念。结合后文的收录条件，这更像 agent 的自查，并未明确要求每次询问用户；[ADR 条件](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#offer-adrs-sparingly)也给出全部满足才行动、缺少任一条件就跳过的标准。Astra 文章没有专门倡导自问句写法。
  - Scope: 用于关键筛选与决策；问题需提供实际判断标准，缺少必要信息时再向用户澄清，避免将每一步扩展成长检查清单。借鉴明确行动条件的方式，具体标准按用途调整，不把 ADR 三项条件搬入所有 skill。

- **例子用于说明预期行为和检验概念边界，数量按区分价值确定。**
  - Basis: Matt 的 [domain-modeling](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#discuss-concrete-scenarios)既给出提问示例，也要求执行时构造具体场景检验关系。讨论中区分了写给 agent 的指令示例与面向用户的场景讨论；Astra 文章没有直接提出多举例或增加此类交互的建议。
  - Scope: 示例应帮助理解通常情况、区分相邻概念或发现边界问题；概念澄清应检查定义及其关系能否解释具体情况，不能只统一名称或润色定义句子。换名称却重复同一判断的例子价值有限，避免将某个例子扩展为通用领域规则。

- **发现当前表达、已有约定与实际情况不一致时，可以明确指出差异，再澄清需要调整哪一方。**
  - Basis: Matt 的 [术语表核对](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#challenge-against-the-glossary)和[代码核对](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#cross-reference-with-code)要求发现冲突后主动提出。本次讨论将其概括为适用于不同场景的核对方法。
  - Scope: 检查会影响当前工作的实际矛盾，说明具体差异，不预设用户说法、已有记录或实现中任何一方必然正确；相关材料按当前任务选取。

- **每种产物应承担清楚的职责，区分定义、决定及依据、已验证结果和尚未解决的问题。**
  - Basis: Matt 的 [术语表内容边界](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#update-glossarymd-inline)明确排除规格说明、临时笔记和实现决策，另以 ADR 保存决策理由。本次讨论结合 structure 的现有记录类别提出这一参考。
  - Scope: 按内容用途选择已有的承载位置，减少混杂与重复；未解决问题是否长期保存取决于其对后续工作的影响，不因此自动新增文件类别。

- **有明确内容时再创建文件，结果形成后及时给出可审阅的记录或修订。**
  - Basis: Matt 的 [文件结构](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#file-structure)要求按需创建文件，[术语表更新](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#update-glossarymd-inline)要求含义明确后立即处理、不积攒更新。先呈现可审阅内容并按授权保存，是本次讨论结合项目确认方式作出的调整。
  - Scope: 避免提前铺设空文件，也避免已经明确且有持续价值的结果仅留在聊天中；实际写入遵循适用的授权与记录规则。

- **说明能力边界时，可以区分单纯使用已有信息与需要开展的深入工作。**
  - Basis: Matt 的 [domain-modeling 引言](../../references/matt-skills/upstream/skills/engineering/domain-modeling/SKILL.md#domain-modeling)明确区分读取术语表与主动改变领域模型。本次讨论将这种区分推广到职责相近的 skill。
  - Scope: 澄清确实会影响调用或行为的职责区别，例如解释材料、安排学习过程和保存跨会话记录；控制说明篇幅，不穷举无关排除项。
