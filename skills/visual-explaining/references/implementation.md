# Implementation

## Delivery

Reuse the existing project and authoring workflow when available. Choose a standalone page or a framework project according to the explanation's needs and the cost of building, revising, and validating it. Frameworks, build steps, and local servers are acceptable; give reproducible opening or startup instructions.

## Reuse

Prefer maintained, widely used libraries and available skills when they reduce work. Check the particular resource's fit and maintenance, rather than inferring them from a parent repository's popularity. Consult [Sources](sources.md) when choosing a reference; no third-party skill is a required dependency.

## State and views

Keep model rules, visual rendering, and explanation content identifiable and consistent. Guided steps and learner actions use the same rules; all views and explanations reflect the current model state. For preset demonstrations, clearly state which behavior is scripted and which inputs can actually change outcomes.

Use stable states or replayable actions for meaningful back, reset, and comparison behavior. Separate teaching simulations from target-system execution and retain their stated boundaries.

## Reading and feedback

Keep the current question, model, and relevant explanation close together. Expose supporting definitions and sources without losing the reader's place. Provide keyboard alternatives, readable narrow layouts, and reduced-motion behavior.

Let learners bring a reproducible scenario, their actions, reasoning, assistance, and questions back to the conversation, for example through a copyable summary. Treat only shared or inspected attempts as learning evidence.
